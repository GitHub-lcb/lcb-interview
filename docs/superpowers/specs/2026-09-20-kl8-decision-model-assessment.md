# 快乐8号码概率推算接入决策模型 —— 可行性评估与接入方案

> 评估对象：在 `tools/lottery/kl8` 中使用新一代决策模型（GBDT、序列深度模型、强化学习等）做号码概率推算。
> 结论日期：2026-09-20　依据：当前代码 + 概率论边界。

## 0. 一句话结论

**换成更强的模型不会提高命中率。** 快乐8 是独立同分布抽样，任何模型对"下一期开哪些号"的可预测性上限是 0。
现有系统已经是"6 因子加权 + 走查前推择优"的模型，把线性加权换成 GBDT，本质只是换一个打分函数，期望不变。

真正值得做的是把模型用在四个**非预测**落点上：组合覆盖优化、不确定性校准、随机性审计、下注决策层。
其中只有**组合覆盖优化**能带来统计上真实的收益（因为它是组合数学，不是随机问题）。

---

## 1. 先分类：哪些是"预测"，哪些是"决策"

| 子问题 | 数学性质 | 模型能否改善 | 现有系统 |
|---|---|---|---|
| 下一期某号是否开出 | i.i.d.，P = 20/80 = 0.25 | **不能** | 正走在这条路上 |
| 一组号码的命中数 | 超几何分布 | 不能改期望，只能改方差 | `hitDistribution` |
| 号码组合的覆盖结构 | 组合优化问题 | **能** | Lab 有部分覆盖 |
| 置信度表述是否诚实 | 校准 / 不确定性量化 | **能** | 硬编码 低/中低/中 |
| 开奖数据是否真随机 | 假设检验 | **能**（唯一可能出真信号处） | 无 |
| 负 EV 下选多少注 | 效用最大化 | **能**（决策层） | 无 |

把"选号"从**预测问题**重新定义为**决策问题**，模型才有立足点。这正是"决策模型"这个词的本义。

---

## 2. 数学边界：多小的优势才"测得出"

选4 单号命中 p = 0.25，每组每期期望命中 1.00 个，标准差 σ = √(4 × 0.25 × 0.75) = 0.866。

在 95% 置信下检测相对提升 δ，所需期数 n ≈ (1.96 × 0.866 / δ)²：

| 相对提升 | 单号命中率 | 所需期数 | 快乐8 每天 1 期 ≈ |
|---|---|---|---|
| +10% | 0.2750 | ≈ 288 | 0.8 年 |
| +5% | 0.2625 | ≈ 1,153 | 3.2 年 |
| +2% | 0.2550 | ≈ 7,200 | 19.7 年 |
| +1% | 0.2525 | ≈ 28,800 | 79 年 |

**任何小于 5% 的真实边际，在有生之年无法被验证。** 而 5% 的相对命中提升，相对官方奖金结构（总体返奖率显著低于 100%）也没有财务意义。

所以"用更强的模型提高命中概率"不是难，是**数学上不通**。声称做到了的，要么过拟合，要么把回测噪声当信号。

## 4. 逐类模型给判断

| 方案 | 代表 | 实际增量 | 代价 | 判断 |
|---|---|---|---|---|
| 梯度提升树 | XGBoost / LightGBM / CatBoost | ≈ 0：i.i.d. 目标下树只拟合噪声 | 中（需推理服务或 PMML） | ❌ 不做 |
| 序列深度模型 | LSTM / Transformer / Informer / TimesNet | ≈ 0：纯随机序列无可学时间结构 | 高（Python 推理 + 重依赖） | ❌ 不做 |
| 强化学习 / Decision Transformer | DQN / MCTS | 选号层无意义；下注层有意义（见 §5.D） | 高 | ⚠️ 仅限决策层 |
| 类型化决策模型 | **Jev（TypeSafe System One）** | 命中率增量 ≈ 0，但**工程增量真实**：类型化输出免 JSON 容错、单次 81 问并行、成本极低，可支撑校准与审计 | 低（JDK 内置 HttpClient，无新依赖） | ✅ 已接入，见下 |
| 贝叶斯层次 / 共轭先验 | Beta-Binomial、Dirichlet | **有意义**：把"中低"换成校准后的后验区间 | 低（纯 Java） | ✅ 推荐 |
| 假设检验 | 卡方 / KS / 游程 / NIST SP800-22 | **有意义**：唯一可能发现真信号处 | 低（纯 Java） | ✅ 强烈推荐 |
| 组合优化 | ILP / 遗传 / 模拟退火 / 贪心覆盖 | **有意义**：不改期望，降下尾风险 | 低–中（纯 Java） | ✅ 推荐 |
| LLM | 已在用 | 用来说人话和反证，不用来算 | 已有 | ✅ 保留 |

### 4.1 关于 Jev 的补充结论

Jev 是"状态 + 类型化问题 → 类型化答案 + 校准概率"的决策层，不是时序预测模型。
它无法突破 §2 的数学边界——单号真实概率恒为 0.25，Jev 的概率推算也不会改变它。
但它在**工程侧**确实有真实增量，因此已经接入：

| 能力 | 价值 |
|---|---|
| `Noul` 一次并行问 80 个号码 | 一份结构稳定的 80 维概率分布，无需解析 JSON |
| 返回校准概率与置信度 | 直接支撑 §5.B 的不确定性表述 |
| 单次调用 ~70–500ms、$0.042/MTok | 成本低到可以逐期回放，支撑校准闸门 |
| 与现有 LLM 链路解耦 | 任一链路缺失不影响另一条 |

接入实现详见 `2026-09-20-kl8-jev-integration-design.md`。
关键设计：`JEV_ALLOW_SCORING` 默认关闭，只有在
`POST /api/tools/lottery/kl8/jev/calibration` 明确判定"显著优于 25% 随机基线"后才由人打开。
按 §2 的数学预期，这个闸门**应当**长期保持关闭——这正是它存在的意义。

## 5. 真正值得做的四个落点

### A. 组合覆盖优化（唯一"模型越强结果真越好"的方向）

不改 EV，改**命中分布的形状**：在注数预算内最大化"至少一组中 ≥ 2"的概率（选4 的首个有奖级别是中2）。

理论值（超几何分布，2 注选4）：

| 策略 | P(至少一组中 ≥2) |
|---|---|
| 两注是同一组号码 | 25.9% |
| 两注号码完全不重叠（覆盖 8 个号） | **46.9%** |

差距接近一倍——这跟"预测"无关，纯粹是覆盖结构问题。

- 输入：候选池 score（现成）、`pairCounts` 共现矩阵（现成）、注数预算 B。
- 目标：max P(∃ 组命中 ≥ k)，s.t. 注数 ≤ B。
- 求解：先按 score 贪心 + 2-opt 换号局部搜索；B 较大时上 ILP 或模拟退火。
- 落点：`LotteryKl8LabService` 新增 `COVERAGE` 变体，复用现有 `LabVariant` 展示。

### B. 不确定性校准

`confidenceLabel` 现在只有 低 / 中低 / 中 三档硬编码语义，改成**校准后的后验**：

- Beta-Binomial：先验 Beta(α₀, β₀)，观测 n 期命中 k 次 → 后验 Beta(α₀+k, β₀+n−k)。
- 输出不是"置信度"这种模糊词，而是"95% 后验区间 [24.1%, 26.3%]"。
- 真值是 25%，这个区间会**自己说明"没有信息量"**——这才是诚实，同时消掉"置信度在骗人"的合规风险。

### C. 随机性审计（唯一可能发现真 alpha 的地方）

若数据源被篡改、抓取错期、或 RNG 真有偏，**这是唯一能被抓到的东西**：

| 检验 | 抓什么 | 实现 |
|---|---|---|
| 卡方拟合优度（80 桶） | 号码整体是否均匀 | 纯 Java |
| KS 检验 | 分布形态偏移 | 纯 Java |
| 游程检验 | 序列相关 | 纯 Java |
| 滞后相关 | 上期是否影响下期 | 纯 Java |
| 和值 / 奇偶 / 区间分布 | 结构性偏差 | 纯 Java |
| NIST SP 800-22 子集 | 完整随机性套件 | 可选 |

每项输出统计量、p 值、中文结论。这同时是**数据质量看门狗**——比任何"预测模型"都实在。

### D. 决策 / 资金层

把"买哪几注"建成负 EV 下的效用最大化：风险偏好（EV / 方差 / 下尾）作主目标，预算约束下的覆盖最大化 = A 的目标。
终局必须明说："任何策略期望回报都是负的，模型只能改变输钱的节奏和方差。"
合规：**不做自动投注**，只做模拟与教育。

## 6. 工程接入方案（最小改动）

新增策略接口，让"模型"与"规则"在同一栅栏下竞争：

```java
/**
 * 号码打分策略。任何决策模型只要实现该接口，即可接入现有回测栅栏。
 */
public interface LotteryKl8NumberScorer {

    /** 策略版本标识，写入 recommendation.strategy_version。 */
    String version();

    /** 对 80 个号码打分，分数越高越应入选。 */
    Map<Integer, Double> score(LotteryKl8FeatureReport report);
}
```

- `RuleFactorScorer`：包装现有 6 因子加权，行为不变（默认实现）。
- 新实现：`BayesianScorer`、`CoverageScorer` 等。
- 接入点：`LotteryKl8FeatureService.buildReport()` 的候选池构造改为调用注入的 `List<LotteryKl8NumberScorer>`。
- **自动否决闸门**：任何新 Scorer 上线前必须过 walk-forward 回测，且要求 out-of-sample 的 95% 置信区间**不覆盖 25% 基线**；否则拒绝合并。按 §2，样本量下这几乎不可能达成——等于自动锁死"伪科学上线"。

改动清单：

| 文件 | 改动 |
|---|---|
| `service/LotteryKl8NumberScorer.java` | 新增接口 |
| `service/RuleFactorScorer.java` | 新增，包装现有因子逻辑 |
| `service/LotteryKl8BayesianCalibrationService.java` | 新增，后验区间 |
| `service/LotteryKl8RandomnessAuditService.java` | 新增，随机性检验 |
| `service/LotteryKl8FeatureService.java` | 候选池构造改走 Scorer |
| `dto/tools/LotteryKl8LabRequest.java` | 新增 `COVERAGE` 变体 |
| `controller/tools/LotteryKl8Controller.java` | 新增 `GET /api/tools/lottery/kl8/audit` |
| `frontend/src/components/LotteryKl8LabPanel.tsx` | 新增"随机性审计"页签 |

## 7. 验收标准

1. **随机性审计**：对现有全部历史开奖跑一遍，输出各项 p 值；预期结论为"未发现显著偏差"。
2. **校准**：新后验区间覆盖 25% 真值，且区间宽度随样本量收敛。
3. **覆盖优化**：相同注数下，"至少一组中 ≥2"的模拟概率相对朴素随机组合有统计显著提升（这一条能达标，因为是组合数学）。
4. **任何预测型模型**：过不了 §6 闸门的一律不合并。
5. `mvn test` + `npm run build` 通过。
